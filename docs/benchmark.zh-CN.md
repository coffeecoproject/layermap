# LayerMap 对比实验报告

[English](benchmark.md) · [中文](benchmark.zh-CN.md)

代码地图能不能帮编程 agent 回答"改这里会影响什么"？我们做了四组实验：

1. **限定预算对照**：同一个模型，每次作答最多 15 次请求，分别在用和不用 LayerMap 的条件下作答。6 道公开题里，
   用地图找到了 **97.9%** 的受影响 HTTP 接口，不用地图找到 **58.8%**。
2. **自然使用**：不告诉 Claude Code 和 Codex 有地图。装了插件后，12 次运行里 **12 次**都主动用了地图；用 0.1.5
   复测，又是 12 次中 12 次。不限请求次数时：
   - 有没有地图，准确率相同（98–100%）；
   - Claude Code **花费少约三分之一**；
   - Codex 在最高推理强度下**输入 token 少 55%**，但用现在更省的默认设置时反而多 14%（见[复测](#用-015-复测)）；
   - 用时多 17–25%。

3. **改完自检的准确性**（不用模型）：每次让一个函数一进入就失败，再跑项目全部测试。真正失败的测试文件里，
   `project_check_changes` 在 Miniflux（Go）上列出了 **100%**；在 Starlette（Python，测试放在单独目录）上
   用 0.1.10 直接列出 **94–98%**，加上间接导入的为 **97–99%**（之前为 83–88% 和 90–98%）。
4. **波及任务**：最省事的改法会改坏别的功能的需求。用 0.1.8 和 0.1.9 的改完自检，Codex 用地图时 24 次里有 **23 次**
   没有碰坏任何别的功能的测试，不用时 12 次里 3 次。Claude Code 没有明显差别（24 次里 11 次，12 次里 4 次）：它看到了
   自己改了哪些别的功能的测试，但有意保留了范围更大的改法，并说明了原因。用 0.1.7 的自检时，地图没有带来差别。

样本量小，题目也由 LayerMap 作者编写，请先看[局限](#局限)。题目原文、标准答案和评分规则都在
[`benchmark/tasks`](benchmark/tasks)。

## 题目

每道题指定一个函数，问修改它会影响哪些 HTTP 接口，要求写出每个接口的调用链和没能确认的地方。题目不提地图。
题目原文是中文，题目文件里附有英文翻译。

| 题目 | 语言 | 项目 | 修改对象 | 接口数 |
|---|---|---|---|---|
| [SRCSET_PARSE](benchmark/tasks/SRCSET_PARSE.json) | Go | [Miniflux](https://github.com/miniflux/v2) v2.2.17 | `ParseSrcSetAttribute` | 29 |
| [ENTRY_QUERY](benchmark/tasks/ENTRY_QUERY.json) | Go | Miniflux v2.2.17 | `EntryQueryBuilder.GetEntries` | 36 |
| [TAX_SERVICE](benchmark/tasks/TAX_SERVICE.json) | Python | [Polar](https://github.com/polarsource/polar) `server/` @ `71bd203` | `_get_tax_service` | 21 |
| [METER_FILTER](benchmark/tasks/METER_FILTER.json) | Python | Polar `server/` @ `71bd203` | `FilterClause.matches` | 20 |
| [RETRY_DELAY_CAP](benchmark/tasks/RETRY_DELAY_CAP.json) | Java | [Conductor](https://github.com/conductor-oss/conductor) v3.32.5 | `DeciderService.applyMaxRetryDelayCap` | 20 |
| [SECRET_REF](benchmark/tasks/SECRET_REF.json) | Java | Conductor v3.32.5 | `ParametersUtils.resolveSecretRef` | 22 |
| TS-A | TypeScript | 未公开代码库 | 一个业务日期比较函数 | 33 |
| TS-B | TypeScript | 未公开代码库 | 一个审计事件写入函数 | 22 |

受影响接口距离目标 1 到 12 层调用。有些只能经由模板函数、类层次中别处实现的接口，或隐式调用的 `__aexit__` 到达。

**标准答案**：两份来源逐个接口核对，不一致的地方回源码核实。其中一份是独立工具链的结果：

- Go：`golang.org/x/tools` 的 VTA 调用图；
- Python：mypy，并补上 FastAPI 的 `Depends` 依赖；
- Java：Conductor 自己的 Gradle 构建编译出的字节码。

另一份是 LayerMap 自己的索引。

Python 的两道题在第一轮后修订过，原因记录在题目文件里：

- TAX_SERVICE：有一个接口运行时到不了，22 改为 21；
- METER_FILTER：有一个接口经由隐式的 `__aexit__` 到达，19 改为 20。

**计分**：

- 列为受影响且调用链等价：1 分；
- 标为不确定，或调用链错误、缺失：0.5 分；
- 遗漏：0 分；
- 把标准答案以外的接口说成确定受影响：记一处误报。评审回源码确认确实会到达的除外。

**评审是盲评**：每道题的答案打乱后用随机字母编号，交给一个 Claude Opus 5.5 agent 评审。评审能看到标准答案，
可以只读查看源码，但不知道哪个答案来自哪一组。

## 实验一：限定预算对照

**条件**：

- **模型**：`gpt-5.5`，推理强度 high，在一个最小的实验程序里通过 OpenAI Responses API 调用。
- **两组共有**：四个只读源码工具（列文件、查路径状态、精确文本搜索、读文件）。
- **地图组额外**：
  - 加上地图的三个工具；
  - 加一句说明：`project_explore_map` 可以查看调用方和被调用方；
  - 第一次请求必须调用地图。
- **预算**：每次作答最多 15 次请求，最后一次不提供工具。
- **次数**：每题每组 3 次，顺序随机，每次在只能看到项目文本文件的沙箱里运行。48 次全部完成，只看源码组有 1 次
  超时，记 0 分。

| 题目 | 接口数 | 用 LayerMap | 只看源码 |
|---|---|---|---|
| SRCSET_PARSE（Go） | 29 | 29 / 29 / 29，**100%** | 23.5 / 18.5 / 24，75.9% |
| ENTRY_QUERY（Go） | 36 | 36 / 36 / 36，**100%** | 35 / 36 / 35，98.1% |
| TAX_SERVICE（Python） | 21 | 16 / 20 / 19，**87.3%** | 6.5 / 7.5 / 4.5，29.4% |
| METER_FILTER（Python） | 20 | 20 / 20 / 20，**100%** | 1 / 1 / 1，5.0% |
| RETRY_DELAY_CAP（Java） | 20 | 19.5 / 20 / 19.5，**98.3%** | 6 / 0（超时）/ 12.5，30.8% |
| SECRET_REF（Java） | 22 | 21.5 / 22 / 22，**99.2%** | 18 / 13 / 18，74.2% |
| **6 道公开题合计** | 444 | **434.5，97.9%** | 261，58.8% |
| TS-A（未公开） | 33 | 33 / 33 / 33，100% | 12.5 / 17.5 / 11，41.4% |
| TS-B（未公开） | 22 | 22 / 22 / 22，100% | 17 / 18.5 / 15，76.5% |

**误报**：

- 用 LayerMap：18 份公开题答案共 4 处。
  - 1 处是 Miniflux 的分享页：它走的分支不做 srcset 改写。
  - 3 处是 Polar 的后台管理接口：静态上相连，但运行时不会触发计费。
- 只看源码：共 6 处，其中两份答案各编造了一个 Conductor 里不存在的接口。

**差距来自离目标远的接口**：

- METER_FILTER：只看源码的答案都找到了所有路径汇聚的那个函数，但 15 次请求内没能把它的调用方追到任何接口。
- RETRY_DELAY_CAP：只看源码的答案漏掉了大部分 9 层以上的接口。
- TS-A：有 7 个接口超出一次 8 层视图的范围。用 LayerMap 的答案顺着视图里"未展开"的声明继续追，每次都全部找到；
  只看源码的 3 次合计找到 21 个中的 2 个。
- ENTRY_QUERY：接口都在 1–3 层以内，两组都答得好。

**token 消耗**：请求次数封顶时，用 LayerMap 的作答输入 token 更多，因为深层地图视图较长，模型看完还要读源码核实。

- 6 道公开题合计：642 万对 516 万，多 24%；
- 按题看：0.57 倍（ENTRY_QUERY）到 2.19 倍（RETRY_DELAY_CAP）；
- 模型用时差不多：3,001 秒对 3,179 秒。

在这种设定下，地图换来的是准确率，不是省钱。

## 实验二：Claude Code 和 Codex 的自然使用

**条件**：

- **Agent**：
  - Claude Code 2.1.278，默认模型（记录为 `claude-opus-5`）；
  - Codex CLI 0.157.1，作者的默认配置，推理强度 max，模型名称未记录。
- **题目**：6 道公开题，问题原文相同，不提地图。
- **有地图**：LayerMap MCP 服务（地图已预先建好），加上插件附带的一句提示：

  > The layermap MCP server is available here. For questions about what calls a function, what a
  > change affects or where code is used, start with its project_explore_map tool (direction
  > INCOMING, depth up to 8) before grep, then confirm in source.

- **没地图**：既没有服务，也没有提示。
- **运行方式**：只读权限，不限请求次数，每次最多 45 分钟；每格只跑 1 次，按同样方式盲评。

**会不会主动用地图**，取决于地图怎么提供：

| 提供方式 | Claude Code | Codex |
|---|---|---|
| 只提供工具，用最初的工具说明 | 2 次中 0 次 | 1 次中 0 次 |
| 工具说明开头写清何时使用 | 1 次中 1 次 | 1 次中 0 次 |
| 上述说明加一句提示（插件现在的做法） | **6 次中 6 次** | **6 次中 6 次** |

Codex 配置的工具较多时，要先"搜索工具"才能看到 MCP 工具，是那句提示让它去找地图。加了提示后：

- Claude Code 在第 2–3 次调用时用上地图；
- Codex 第 1 次调用就用地图。

**准确率与消耗**（共 147 个接口。这里 METER_FILTER 按原来的 19 个接口计分，4 份答案也都找到了第 20 个）：

| | Claude Code 有地图 | 没地图 | Codex 有地图 | 没地图 |
|---|---|---|---|---|
| 找到的接口 | 146（99.3%） | 145.5（99.0%） | 144（98.0%） | 145（98.6%） |
| 误报 | 0 | 0 | 0 | 0 |

| | 有地图 | 没地图 | 变化 |
|---|---|---|---|
| Claude Code 花费 | $12.60 | $18.40 | **−32%** |
| Codex 输入 token | 1,063 万 | 2,348 万 | **−55%** |
| Claude Code 用时 | 2,313 秒 | 1,866 秒 | +24% |
| Codex 用时 | 4,199 秒 | 3,594 秒 | +17% |

**怎么理解**：

- **准确率**：不限时间时，有没有地图都几乎能找全。Codex 有地图那组少的 3 分，是业务逻辑上的判断失误，地图上
  完整显示了那条调用链。
- **花费**：地图让查找过程更短。Codex 省下的 token 大部分在 METER_FILTER：242 万对 1,029 万。
- **用时**：变长是因为有地图后 agent 查得更广。比如 Codex 有一次调用了 84 次工具，其中 23 次是地图。每次查地图前
  检查文件变化，在这几个项目上约 1 秒。

### 用 0.1.5 复测

0.1.5 给每个处理函数标出 HTTP 方法和完整路径，并去掉了每次查询都重复的说明文字。2026-10-07 用同样的 6 道题、
同样的方法重跑并盲评：

- **Claude Code** 2.1.278，模型相同，只跑有地图的一组，以第一轮的无地图结果为基准。
- **Codex CLI** 0.160.1，用作者现在的默认设置（模型 `gpt-6-astra`，推理强度 xhigh；第一轮是最高强度 max），
  有地图、无地图都跑，只在本轮内比较。有地图时用被测版本替换已装插件的服务；无地图时关闭全部插件。

| | Claude Code 有地图 | Codex 有地图 | Codex 无地图 |
|---|---|---|---|
| 找到的接口（共 147 个） | 147（100%） | 147（100%） | 147（100%） |
| 误报 | 1 | 0 | 0 |
| 地图调用 / 其他工具调用 | 41 / 142 | 36 / 103 | 0 / 159 |
| 用时 | 2,329 秒 | 2,264 秒 | 1,883 秒 |
| 花费 | $12.32 | 555 万输入 token | 486 万输入 token |

Claude Code 的 1 处误报是实验一里出现过的 Miniflux 分享页。

**有什么变化：**

- **Claude Code**：其他工具调用比 0.1.4 少（142 对 185），地图调用变多（41 对 27）；用时和花费与第一轮基本
  相同（2,313 秒、$12.60）。和不用地图比，花费少 33%，用时多 25%。
- **Codex**：现在的默认设置自己就查得很省，不用地图只用 486 万输入 token，最高推理强度时是 2,348 万。有地图时
  其他工具调用少 35%，但输入 token 多 14%，用时多 20%。

## 实验三：改完自检的准确性

`project_check_changes` 列出的相关测试，能不能覆盖这次改动可能改坏的测试？参照测试影响分析工具的“模拟器”
做法，不用模型，直接拿检查结果和测试的真实表现对比：

1. 随机挑一个函数或方法，让它一进入就失败（Go 用 `panic`，Python 用 `raise`）；
2. 对这次改动运行 `project_check_changes`；
3. 跑项目全部测试，记下失败的测试文件；
4. 还原文件。每组 60 个函数，随机种子固定。

| 项目 | 测试文件数 | 有测试失败的样本 | 失败的测试文件被列出 | 每次列出（中位数） |
|---|---|---|---|---|
| [Miniflux](https://github.com/miniflux/v2)（Go） | 71 | 60 个中 22 个 | **33 个中 33 个（100%）** | 3 |
| [Starlette](https://github.com/Kludex/starlette)（Python）第 1 组 | 31 | 60 个中 60 个 | **167 个中 163 个（97.6%）**；含间接导入 99.4% | 10 |
| Starlette 第 2 组 | 31 | 60 个中 58 个 | **245 个中 231 个（94.3%）**；含间接导入 96.7% | 13 |

“被列出”指 RELATED TESTS 清单；“含间接导入”另外加上检查只给出数量的那些测试文件。清单宁多勿漏：在
Starlette 上约占全部测试文件的三分之一。在这两个项目上，一次检查的中位用时为 2–4 秒。Starlette 两行是 0.1.10 的结果；
同样的样本在 0.1.9 上直接列出 88.1% 和 82.9%，当时 Python 分析还不把"类作为参数传递"（pytest 夹具里传给
`functools.partial`）记为一次使用。

Starlette 上剩下的漏报，是框架运行时经 ASGI 协议发起的调用（`receive`、`__aenter__`），以及上传文件时调用的文件方法。
没有任何测试会执行到的函数（Miniflux 上 60 个中有 38 个），只能靠检查列出的受影响入口去核对。

## 实验四：波及任务

改完自检能不能防止 agent 改坏不该改的功能？每道题都是对一个公开项目提出的需求，最省事的改法会改动共用代码，
把别的功能的测试改坏。例如"RSS 里的协议相对链接要沿用订阅源的 http"：共用的网址处理函数同时服务 HTML
内容清洗，而内容清洗要继续把这类链接升级为 https。

- **参与者**：Claude Code 和 Codex（`gpt-6-astra`，推理强度 xhigh），分别用 LayerMap（Claude Code：插件及其结束前提醒；
  Codex：服务和插件的说明文字）和不用。每次运行用全新的仓库副本，最长 30 分钟。
- **计分**：恢复项目原有的测试文件（所以改写别的功能的测试等于改坏它），加入隐藏的验收测试，跑全部测试。验收测试
  通过、且没有其他测试失败，才算“没有碰坏”。其中一道题需求功能自己的测试必须修改，不计入。

**第一轮**（0.1.7；Starlette 和 Miniflux 各 6 道，每道一次）：没有差别。8 道题所有运行都没有碰坏东西。Claude Code
用和不用地图各改坏 5 个测试；Codex 用地图反而改坏更多，其中一次编译不过。Codex 没有跑测试，因为项目所有者的全局
说明规定没被要求就不跑；自检列出的相关测试太多，真正的风险被淹没了。

0.1.8 改进了自检：列出哪些功能区域（包或模块）的测试会经过改动的代码，并说明需求之外的区域的测试失败，意味着改动
波及了它；构造函数不再被当成会通过基类分派；相关测试清单更短；Go 里读取包级变量和常量也会被记录。

**第二轮**（0.1.8；第一轮里有人踩坑的 5 道题，每道题、每个 agent 用和不用各跑 3 次；每个需求都加一句"可以跑项目的
测试来验证"）。没有碰坏的运行次数：

| 题目（项目） | Codex 用地图 | Codex 不用 | Claude Code 用地图 | Claude Code 不用 |
|---|---|---|---|---|
| RSS 协议相对链接保留 http（Miniflux） | **3/3** | 0/3 | 1/3 | 0/3 |
| 读懂 JSON Feed 的两位年份日期（Miniflux） | **3/3** | 0/3 | 2/3 | 1/3 |
| Invidious 播放器改为 640×360（Miniflux） | 3/3 | 3/3 | 2/3 | 0/3 |
| 静态文件不带默认字符集（Starlette） | **2/3** | 0/3 | 2/3 | 3/3 |
| **合计** | **11/12** | 3/12 | **7/12** | 4/12 |
| 静态文件使用弱 ETag（Starlette），不计入 | 0/3 | 0/3 | 0/3 | 0/3 |

- 每次运行都完成了需求。
- **Codex**：用地图时，它只改需求功能自己用的代码；不用时，它改动共用代码，再把别的功能的测试改掉让它通过。这么大的
  差距不太可能是偶然（Fisher 精确检验，p = 0.003）。
- **Claude Code**：差距可能是偶然（p = 0.41）。用地图却碰坏的 5 次里，有 4 次自检已经列出了共用的功能区域，Claude Code
  仍然改写了别的功能的测试。
- **弱 ETag** 不计入：RFC 9110 规定按修改时间生成的 ETag 都是弱的，所以改动所有文件响应共用的生成函数也说得通。两个
  agent 的每次运行都这样改了。
- **代价**：用地图时，Claude Code 用时多 54%、花费多 29%；Codex 用时多 27%、token 多 14%。

0.1.9 会点名这次改动改过的原有测试（逐个比较测试改动前后的代码），并让 agent 在改完后只调用一次自检。

**第三轮**（0.1.9；同样 4 道题，用地图每道跑 3 次；不用地图的数据沿用第二轮）。12 次中没有碰坏的次数：

| | 不用（第二轮） | 用 0.1.8（第二轮） | 用 0.1.9（第三轮） |
|---|---|---|---|
| Codex | 3 | 11 | **12** |
| Claude Code | 4 | 7 | 4 |

- **Codex**：用地图 24 次里 23 次，不用 12 次里 3 次（p < 0.001）。
- **Claude Code**：24 次里 11 次，对比 12 次里 4 次，很可能只是偶然（p = 0.72）；第二轮和第三轮设置几乎相同，结果却从
  7 次变成 4 次。第三轮每次碰坏时，自检都点名了它改过的别的功能的测试。Claude Code 是有意保留这个改动，并在回答里说明，
  同时提出可以改成范围更小的做法：它认为应该在共用代码里修，这正是项目所有者全局说明的要求（"找真正的负责代码，不要堆补丁"）。
  另有两道题本身可以两种理解："文章链接"是否包括文章正文里的链接，经 Invidious 播放的 YouTube 链接算不算"Invidious 播放器"。
- **用时**：Claude Code 用地图的总用时比第二轮少 22%，花费差不多；Codex 用时基本不变。

## 局限

- **样本量小**：
  - 实验一每种语言 2 道题，每组 3 次；
  - 实验二每格 1 次，两种条件在不同时间运行，多数是有地图的先跑。同一道题单次运行的波动很大：复测中有一份
    Claude Code 答案用了 665 秒，第一轮是 359 秒。
- **只测了一类任务**：都是追到 HTTP 接口的影响范围分析，正是 LayerMap 擅长的。
- **实验四每组只跑 3 次**。第二轮的题目是看过第一轮结果后、挑 agent 踩过坑的题，并且由 LayerMap 作者编写。两轮的
  需求说明也不同（第二轮允许跑测试），所以只能在同一轮内比较；第三轮沿用第二轮不用地图的数据。计分把任何对别的功能
  测试的改动都算作改坏，即使 agent 给出理由并做了说明；agent 也继承了项目所有者的全局说明。
- **实验三只覆盖两个项目**（Go 和 Python）。“一进入就失败”只能说明哪些测试会执行到这个函数，不能说明它们能不能发现更细微的错误。
- **题目和标准答案**：题目由 LayerMap 作者编写，标准答案的两份来源之一是 LayerMap 的索引。不一致处都回源码核实过，
  修订也都写明了。
- **评审是模型**：它不知道答案来自哪一组，但能看到标准答案。
- **两个实验测的东西不同**：实验一强制先调用地图，实验二测的是 agent 会不会自己用。
- **实验二的环境没有完全隔离**：agent 沿用了作者的环境，包括全局说明文件和项目自带的 `AGENTS.md`/`CLAUDE.md`，
  两种条件下相同。第一轮没有记录 Codex 的模型名称，复测前它的默认推理强度也变了。
- **实验一没有记录美元花费**，只有 token 数。
- **TypeScript 题用的是未公开代码库**，只报告汇总分数，之后会补公开项目上的 TypeScript 实验。

## 复现

[`benchmark/tasks`](benchmark/tasks) 里每个文件包含：

- 项目、版本和提交；
- 题目原文和英文翻译；
- 修改对象，以及带调用链的标准答案；
- 中立接口和已核实不受影响的接口；
- 评分规则和修订内容。

实验四的题目在 [`benchmark/ripple`](benchmark/ripple) 里：每道题的需求、最省事的改法、它会改坏的测试、正确改法和隐藏的
验收测试。

实验一的实验程序还没有公开。任何 agent 都可以拿题目作答，再按标准答案计分。
